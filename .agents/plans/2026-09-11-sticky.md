# Sticky positioning implementation plan

Status: **done** (2026-09-11). Spec: `.agents/specs/sticky.md`
(normative; this plan only sequences it).

## Phases (each ends green: `pnpm check` + the visual sweep)

### 1. Probes

- A temporary Docker spec (named to run in the three engines): a
  scroll container with a sticky box, read at scroll offsets that are
  cell multiples — a percent `top` (scrollport or containing block?),
  `top` and `bottom` both set on a box taller than the view, and the
  containing-block clamp with a margin on the box. Findings go into the
  spec's "Browser agreement"; the probe is deleted.

### 2. The rule

- `sticky.ts`: `stickyShift` (per-axis: inset edges against the view
  rectangle, `top`/`left` winning, then the margin-box clamp to the
  containing block — the parent's content box, or the scroller's
  content area extended to `scrollRange` when the parent is the
  scroller), `collectStickyBoxes(root)` (document order, each with its
  ancestor chain), and `applyStickyShifts(boxes)` (painted origins from
  the chains, the nearest scrolling ancestor's scrollport and offset,
  `node.stickyShift` written, deleted when zero). Percent insets
  resolve per the probe.
- `types.ts`: `stickyShift?` on nodes and on inline element records;
  `lattice?` on table nodes.
- `table.ts`: `buildLatticeRuns` becomes lattice geometry (segments
  with their owning node) kept on the table node; `paintLattice` (in
  plain-text.ts beside the decoration runs) places segments with their
  owners' shifts into an arms map and resolves glyphs through
  `junctionGlyph`; the table tests' expected rows stay as they are.
- `sticky.test.ts`: the pure rule and the shifts on built trees with
  `node.scroll` set by hand — the spec's Testing list, the stuck-header
  and stuck-column lattice cases included; `table.test.ts` stays as it
  is, the paint-time lattice reproducing every row.

### 3. Consumers and the native side

- `positioning.ts`: sticky is static in the positioning pass;
  `tree.ts`: an inline sticky element's insets become constraints on
  its record, not offsets; `forEachLeafCell` adds the record's
  `stickyShift`; `render.ts` writes the shift into the inline-inset
  properties (the marker already pins `position: relative`);
  `positioning.test.ts` "sticky behaves as relative for now" becomes
  "a sticky box's insets offset nothing at rest".
- `plain-text.ts` `walk`, `pointer.ts` `hitStack`, `focus.ts`
  `focusableRects`: add the child's `stickyShift` where `localRect` is
  added — one line each, the scroll subtraction beside it.
- `element.ts`: the layout pass collects the sticky boxes beside the
  scroll containers; `applyStickyShifts` after `#syncScrollOffsets` in
  both the layout pass and the scroll repaint; `--mw-sx`/`--mw-sy`
  written on changed sticky nodes (cleared at zero), `takeRecords()`
  after the writes on the repaint path (the layout pass drains
  already); `render.ts` clears both on a box no longer sticky.
- `styles.css`: the geometry rule's `left`/`top` add the shift vars.
- Tests: `hitStack` and `focusableRects` at a pinned heading; the
  transcript with a shift; the native shift vars are checked by the
  stories (the box the browser places lands on the grid's cell after a
  scroll).

### 4. Story, docs, playground

- `Features / Sticky` story: a scrolling list with sticky section
  headings and a sticky footer, the play scrolling natively and
  asserting the grid row and the native box; a bordered table with a
  sticky header and a sticky first column scrolled both ways; its
  golden mid-scroll.
- Docs per the spec's touch points; the playground sample gains a
  sticky section heading in its scrolling article if it reads well.
